# 元曲可恢复估算重算：2,101 / 98.0% 到底是什么（R2-14 / C3）

> 只读复核。分母/分子逐项标注来源文件与 SQL，全部可复算。
> 结论：**2,101 = 1,729 + 372，是两个互不相交的总体的直接相加；98.0% 的分母是 2,143，不是 4,510，也不是 10,685。**
> 该加法把 372 条中 7 条「不是作品」的空记录也算成了可恢复，正确值应为 **2,094 / 2,143 = 97.7%**。

---

## 一、直接回答两个问题

### Q1：2,101 是「1,729 的子集」还是「1,729 + 372」？

**是 `1,729 + 372 = 2,101`，不是子集。**

两批记录**互不相交**，且分处两个总体：

| 成分 | 条数 | 是否在 `works` 里 | 曲文在哪 |
|---|---|---|---|
| `IN_OTHER_FIELD` | 1,729 | **在**（`genre='曲'`，有 `work_id`） | 曲文头在 `title_raw`，余文在 `text_raw` |
| 被 `len(txt_norm)<8` 丢弃 | 372 | **不在**（`works` 无此行） | 曲文头在 raw JSON 的 `title`，余文在 `paragraphs` |

- 1,729 的集合文件：`LOGS/yq_set_4510.txt` 与 `YUANQU_1729_FIELD_BOUNDARY_AUDIT.csv`
- 372 的集合文件：`YUANQU_372_IMPORT_FILTER_AUDIT.csv`（`work_id_or_index = json#<下标>`）
- 二者交集：**0**（372 条根本不在 `works` 中，`work_id` 不存在，不可能与 1,729 相交）

### Q2：98.0% 的分母到底是什么？

分母 **2,143**，是「文本确有缺损、且缺损部分可能存在于本地文件」的**风险总体**：

```
2,143 = 1,729（曲文头在标题，在库）
      +   41（源即短段/残句，在库）
      +    1（纯宾白，在库）
      +  372（被导入过滤，不在库）
```

对应 R2-13 的表述「合计 2,143 / 可恢复 2,101（98.0%）」。

**它既不是 4,510，也不是 10,685：**

| 口径 | 数值 | 含义 |
|---|---|---|
| 全曲集 | 10,685 | `genre='曲'` 全部记录 |
| 审计全集 | 4,510 | 含 2,739 条**曲文本来就在正文**的记录（不缺） |
| 风险总体 | 2,143 | 4,510 中真正有缺损的 1,771 条 + 库外的 372 条 |

所以 98.0% 的分母**只包含「可能缺文」的记录**，把 2,739 条完好的 `LYRIC_PRESENT` 排除在外。这一点 R2-13 的表格写法正确，但正文没有明说分母范围，容易被误读成「4,510 中恢复了 2,101 条（46.6%）」。

## 二、原式逐项复核

### 2.1 原始算式

```
分子 2,101 = 1,729 + 372
分母 2,143 = 1,729 + 41 + 1 + 372
比率 2,101 / 2,143 = 98.04%（R2-13 写作 98.0%）
```

算术本身**无误**，但分子含了不该含的记录（见 2.2）。

### 2.2 发现的问题：372 里有 7 条不是作品

`YUANQU_372_IMPORT_FILTER_AUDIT.csv` 逐条复核后：

| recoverable | 条数 | 说明 |
|---|---|---|
| `Y_TITLE+BODY` | 225 | 曲文头在 `title`，余文在 `paragraphs`，可无损拼接 |
| `Y_TITLE_ONLY` | 140 | 曲文只在 `title`（约 30 字），`paragraphs` 全空；可拼出标题内那一段，**其后是否还有曲文不可判** |
| `N` | 7 | 不是作品：`(残缺)。`×2、空正文+曲牌名×4、一句 3 字残句×1 |

7 条 `N` 的明细（`json#` 为 raw JSON 的 0 基下标）：

| json# | title | 源正文 |
|---|---|---|
| 666 | 诸宫调风月紫云庭・南吕/一枝花 | `(残缺)。` |
| 667 | 诸宫调风月紫云庭・梁州第七 | `(残缺)。` |
| 2338 | 寄生草 | 空 |
| 2745 | 同前 | `……。` |
| 4114 | 仙吕・翠裙腰缠令 | 空 |
| 9896 | 锦云堂暗定连环计・滚绣球 | `油掠的髟。` |
| 10860 | 南吕・十样锦 | 空 |

→ 可恢复的只有 **365** 条，不是 372。

### 2.3 修正后算式

```
分子 2,094 = 1,729 + 365
分母 2,143 = 1,729 + 41 + 1 + 365 + 7
比率 2,094 / 2,143 = 97.71%
```

若进一步要求「拼回后即为完整一曲」（扣掉 140 条 `Y_TITLE_ONLY` 中标题停在半句、余文无从查证的 19 条）：

```
分子 2,075 = 1,729 + 225 + (140 − 19)
分母 2,143
比率 2,075 / 2,143 = 96.83%
```

## 三、1,729 条「100% 可恢复」也要打折

R2-13 称 `IN_OTHER_FIELD` 1,729 条**全部**可逐字复原。全量复核（`YUANQU_1729_FIELD_BOUNDARY_AUDIT.csv`）后，文本本身确实都在本地，但**拼接质量不是单一档**：

| 档 | 条数 | 说明 |
|---|---|---|
| A 完整可拼（曲牌可辨、`ov=0`、正文无前置标记） | 1,662 | `title` 尾与 `text_raw` 首无重叠，直接相接 |
| B 叠字续接（`ov=1`） | 20 | 如「恨绵」+「绵，情脉脉」→「恨绵绵」；**重复字是真字，不可去重** |
| C 接缝重字待判（`ov=2`） | 2 | 「彩衣、」+「彩衣轻纱…」、「<鼻勾>」+「<鼻勾>。」；拼不拼掉这两字需人工定 |
| D 曲牌位空缺且正文以「幺」开头 | 45 | `title_raw` 以「・」开头，曲牌名在上游就丢了；`text_raw` 首字是**下一支曲牌**的「幺」标记。其中 40 条标题停在半句，须先剥离「幺」再拼（否则拼成「玉骢幺嘶」），5 条标题已到句末，「幺」即下一支曲牌，直接拼接即可。**曲文可复原，曲牌不可** |
| 合计 | **1,729** | |

因此准确的表述是：**1,729 条曲文都能从本地拼回；其中 1,662 条零裁量，20 条按叠字直拼，2 条需人工定接缝，45 条拼得回曲文但拼不回曲牌。**

## 四、41 条 `FRAGMENTARY` 的性质复核

41 条全部 `char_count` 9–16，全部以句末标点收尾（所以 R2-13 的「源即截断」不能靠标点判断）。按末段字数拆开看：

| 末段汉字数 | 条数 | 判读 |
|---|---|---|
| 0–2 | 8 | **明显句中截断**：`银须霜鬓，世。`／`许多时缘何未归？眼巴。`／`人无远虑，。` |
| 3–7 | 32 | 短句段，可能本来就短（尾声/煞），**完整与否不可判** |
| 11 | 1 | 更像完整短曲 |

→ 41 条中，**8 条可确认有缺文，33 条只是「短」，不是「缺」**。这不改变可恢复数（都没有第二来源），但改变了「41 条文本残缺」这个说法的强度：它应写作「41 条 ≤16 字的短段，其中 8 条可确认句中截断」。

## 五、最终口径（建议替换 R2-13 第三节的表）

| 项 | 数值 |
|---|---|
| `denominator`（风险总体） | **2,143** |
| `inclusion_criteria` | ① `genre='曲'`；② 曲文不在 `text_raw` 主体（`IN_OTHER_FIELD`）或正文短于 12 汉字（`FRAGMENTARY`/`DIALOGUE_ONLY`）；③ 或 raw JSON 中因 `len(txt_norm)<8` 未入库（372） |

## 六、复算方式

```bash
cd <PROJECT_ROOT>/poetry-database
python3 reports/tasks/2026-11-16/R2-14/LOGS/S1_sets.py      # 三集合与 1,729
python3 reports/tasks/2026-11-16/R2-14/LOGS/S2_boundary.py  # 1,729 边界与接缝
python3 reports/tasks/2026-11-16/R2-14/LOGS/S3_filter372.py # 372 逐条 + 7 条非作品
```

`S3` 的对齐方式：用 `tools/parse.py` 同一套 `extract_items`/`norm_text` 重跑 `raw/poetry/yuanqu/yuanqu.json`，得 `kept=10,685 / skipped=372`，与 `works`（`ORDER BY seq`）逐条比对 `title_raw`、`author_name`、`text_raw`，**10,685 条全等、差异 0**，故 `json#下标` 是确定的，不是模糊匹配。
