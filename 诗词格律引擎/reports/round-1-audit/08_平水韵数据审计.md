# 08 平水韵数据审计

**对应审核**：A07
**结论**：**成立。** v1 声称「平水韵 106 韵全表（8116 字头）」，但从未说明 8116 是什么口径；
核查后发现该数字**既不是韵书原貌，也不是唯一字数**，而是「转简后落在 BMP 范围内的唯一字」。
本轮把口径逐层拆开、把源数据污染与丢失记录在案，并重建了可回溯的索引。
但**韵书本身的来源未核验**，这是本项只能给 `PARTIAL` 的原因。

---

## 一、审核意见

> 8116 个字头必须给出统计口径，包括唯一汉字数、多音多韵记录数、繁简映射和重复项。
> OpenCC 只能用于繁简转写，不能作为古代读音的依据。

## 二、口径拆解（全部可复算）

`tools/build_lexicon.py` 重建过程中的每一步：

| 层级 | 数值 | 含义 |
|---|---|---|
| ① 源文件字头条目 | **10714** | 106 个韵目下所有字符的原始总长（含跨韵重复、含污染字符） |
| ② 减去非汉字污染 | −34 | 入声十七洽尾部混入的拉丁字母 |
| ③ 减去韵内重复 | −32 | 同一韵目内重复出现的字 |
| ④ 有效字头条目 | **10648** | ①−②−③ |
| ⑤ 唯一繁体字 | **8550** | ④ 去重 |
| ⑥ 唯一简体字 | **8361** | ⑤ 逐字 t2s 转写后去重 |
| ⑦ v1 索引收录 | **8116** | ⑥ 减去 245 个扩展区汉字（被 `0x4e00–0x9fff` 过滤器丢掉） |

**「8116 字头」的真实含义 = ⑥ − 245。** 它既不是韵书原貌（10648 条目），也不是唯一字数（8361）。

### 2.1 245 个被静默丢弃的字

v1 的 `build_lexicon.py` 第 62 行：

```python
if not ("\u4e00" <= ch <= "\u9fff"):
    continue
```

这行只放行 CJK 基本区，CJK 扩展 A 区（U+3400–U+4DBF）与扩展 B 区（U+20000 以上）全部被丢弃。
源表里确有 245 个这样的字（多为生僻繁体转简后的结果，如 `𨱓`、`𩭹`、`㲿`）
这些字在韵书里是合法的，在 v1 里不存在，出现的诗会被判「韵书未收录」。

同一问题也存在于 v1 的 `split_lines()`：用同样的范围过滤诗句字符。
**后果更严重** —— 含扩展区字的诗句会被静默删字，导致句长错位，
一首七言可能被当成六言，报出「暂不支持的体式」。本轮已把范围扩到扩展 A/B 区。

### 2.2 34 个污染字符

入声十七洽的原始串末尾：

```
…唼掐PublicdomainPublicdomainfalsefalse
```

这是从某个公有领域资料整理时残留的标记字符串。v1 的过滤器把它当作「非汉字」丢掉，
所以**没有进入索引**，但**源数据文件仍然脏着**。本轮在 `平水韵_数据审计.json` 中逐字登记，
并在重建时显式删除。源文件 `平水韵_全表_繁体.json` **未修改**（保留原样以便复核）。

### 2.3 32 处韵内重复

17 个韵目内存在重复字，最集中的是入声十七洽（除污染外仍有重复）、入声四质（7 字）、上平四支（3 字）。
v1 靠 `if g not in item[tone]` 侥幸去重，但没有计数，无人体察。

## 四、繁简映射（审核要求「OpenCC 不能作为古代读音依据」）

这一条必须正面回答：**本项目没有用 OpenCC 决定读音**。

OpenCC 只做一件事：把韵书里的**繁体字头转成简体字头**，以便用简体输入检索。
读音来自该繁体所在的韵目，不来自转写。

但转写确实带来一个**必须披露的副作用**：

| 指标 | 数值 |
|---|---|
| 繁体归并（≥2 个繁体并为一个简体） | **176** 个简体，共吸收 189 个字形 |
| 归并后出现「平仄兼收」 | **33** 个 |

例：

| 简体 | 来源繁体 | 归并后的声调 | 后果 |
|---|---|---|---|
| 蒙 | 濛、矇、蒙 | 平（一东）＋仄（一董） | 变成「两读字」 |
| 只 | 只、隻 | 仄（四纸）＋仄（十一陌） | 无平仄冲突，但韵部两条 |
| 几 | 几、幾 | 仄＋平（五微）＋仄（四寘） | 变成「两读字」 |
| 据 | 据、據 | 平（六鱼）＋仄（六御） | 变成「两读字」 |

**这 33 个「两读」是转写造成的，不是真两读。** 它们的正确处理需要按繁体分别判定，
即：输入若为简体「蒙」，在没有上下文时无法区分是哪个繁体 —— 这是简体输入固有的信息损失，
不是引擎的 bug，但必须在报告里说明，不能算进「874 个真多音字」里当作正常现象。

（这 33 个已列入 `平水韵_数据审计.json` 的 `繁简归并明细`，可逐条查。）

## 五、v1 数据层的其他问题

| 问题 | 说明 |
|---|---|
| 无来源记录 | `meta` 只写「来源：平水韵_全表_繁体.json」，没有版本、编者、网址、许可 |
| 无 sha256 | 无法证明索引是从哪份源文件生成的 |
| 无繁简回溯字段 | 索引只有简体，无法知道该字来自哪个繁体 |
| 无入声标识 | `ping`/`ze` 二分，入声混在仄里，导致《词林正韵》无法使用 |
| 无统计脚本 | 所有数字（8116、106）都是硬写进 meta 的，不是算出来的 |

v2 索引 `平水韵_索引.json` 的结构：

```json
"东": {"trad": ["東"], "r": [{"g": "上平", "y": "一东"}]}
```

- `trad` 保留繁体，可回溯；
- `g` 保留声部（上平/下平/上/去/入），入声可单独取出，供词林正韵使用；
- `meta` 写入源文件 sha256 与全部统计口径。

## 六、源数据来源核验状态（本项最大缺口）

严格按 `AGENT_REPORTING_STANDARD.md` 第四章的状态词：

| 状态 | 本项目实际达到 |
|---|---|
| FOUND | 是 |
| DOWNLOADED | 是（文件在库内） |
| PARSED | 是（JSON 可解析） |
| READ | 是（逐韵读取、统计、清洗） |
| EXTRACTED | 是（10648 条目、8361 简体） |
| **VERIFIED** | **否** |

**没有做到 VERIFIED。** 具体缺什么：

1. `平水韵_全表_繁体.json` 的**原始出处不明** —— 文件里没有写编者、版本、网址、许可。
2. 韵目内字序与字数**未与任何印本或权威数据库逐韵对勘**。
3. 「收」在去声二十六宥、「留」在去声二十六宥、「乡」在去声二十三漾 —— 这类记录
   我无法判断是真又音还是源数据误收。传统韵书确实广收又音，但本项目没有任何依据可以区分。

第 3 点是硬伤：**874 个平仄兼收字里，有多少是真多音，有多少是数据噪声，本项目答不上来。**
它直接影响判定质量 —— 例如「收」被判为两读，导致「山色苍茫暮雨收」的句子起式一度无法确定
（已改用韵部判入韵，绕开了这个具体字，但绕开不等于解决）。
