# 第五章　技术实现与逻辑

## 5.1 模块结构

| 模块 | 职责 | 核心函数 |
|---|---|---|
| `engine/yunshu.py` | 只做「查」，不做「判」 | `Lexicon.tone_state()` / `.yuns()` / `.cilin()` / `.is_lenient()` |
| `engine/cilin.py` | 十九部映射表 + 自检 | `bu_of()` / `is_half()` / `validate()` |
| `engine/gedou.py` | 判定与呈现 | `check_position()` / `_build()` / `check_poem()` / `check_ci()` / `detect_teao()` / `judge_duizhang()` / `render()` |
| `engine/run_tests.py` | 独立测试 + 不变量 | `judge()` / `invariants()` |
| `tools/*` | 数据构建与审计 | — |

分层的意义：**查不到读音是数据层的事，判不判是逻辑层的事，两者不能互相污染。**
v1 把两者写在一个函数里，才出现了 `realized()` 这种「按谱取音」的写法。

## 5.2 核心数据结构

索引（`平水韵_索引.json`）：

```json
"东": {"trad": ["東"], "r": [{"g": "上平", "y": "一东"}]}
```

- `g ∈ {上平,下平,上,去,入}`，平仄由 `g` 推出：上平/下平为平，上/去/入为仄。
- 入声可单独取出，供词林正韵使用（v1 的二分会丢失这个信息）。

单字判定结果：

```json
{"第": 3, "字": "小", "正格": "平", "实际": "●", "韵书": "上声十七筱",
 "状态": "FLEXIBLE", "说明": "不论位；与正格不同，允许"}
```

## 5.3 判定流程与关键分支

见 `09_代码修复记录.md` 第二节流程图。此处只强调三个判断的**依据来源**：

| 判断 | 依据 | 不是依据 |
|---|---|---|
| 起式（平起/仄起） | 首句第 2 字在韵书中的读音 | 不是「哪种谱失律少」 |
| 首句是否入韵 | 首句末字与第 2 句韵脚是否同属一个平声韵部 | 不是「末字是不是平声」（遇两读字失效） |
| 是否古体 | 偶句韵脚（2/4/6/8 句）是否全为仄声 | 不是「首句入韵与否」（《鹿柴》首句平收会被误判） |

## 5.4 错误分类（审核要求：哪些错来自读音、哪些来自韵部）

| 错误类型 | 来源 | 输出字段 |
|---|---|---|
| 出律 | 平仄（读音已定） | `错误` |
| 失对／失粘 | 第 2 字读音 | `错误` |
| 出韵／落韵 | 韵部 | `错误` |
| 白脚平收 | 声调 | `错误` |
| 孤平／三平调 | 平仄组合 | `错误` |
| 读音未定导致无法判定 | 读音 | `待确认` |
| 半韵导致无法判词韵 | 韵部 | `待确认` |
| 是否三仄尾 | 组合 | `提示`（近体不忌） |
| 重字 | 字形 | `提示` |

**产出的每一条结论都能追溯到「读音」或「韵部」或「组合」三者之一，不混在一起。**

## 5.5 边界条件

| 边界 | 处理 |
|---|---|
| 句数×句长不在四体内 | 抛 `SystemExit`，提示「暂不支持的体式」 |
| 词句式不符 | 判违律，明确「未逐字校验」 |
| 韵书未收录字 | 状态 UNKNOWN，不计通过，末尾列出全部未收录字 |
| 扩展区汉字 | 已纳入字符范围（v1 会静默删字） |
| 两读字位于不论位 | 直接 FLEXIBLE，无需定音（不制造无用 UNKNOWN） |
| 组合规则遇读音未定 | 记待确认，不判违律，也不判通过 |

# 第七章　质量审查与独立性

## 7.1 本轮是否存在自测偏差

**存在，且没有完全消除。**

- 33 个测试样本由执行方选取。
- 期望值（判定码、违律数）由执行方判定。
- 1 个样本（V03）与 2 个注入样本（E03、E07）是执行方构造的。

减轻措施：样本的诗句来自唐宋名篇与《钦定词谱》例词，其格律不由执行方决定；
期望值在引擎改动之前写入 JSON，改动后引擎只能去匹配。
事实证据：三次冲突中两次是引擎错（特拗、相见欢谱），说明样本确实在约束执行方。

## 7.2 是否用同一模型生成与评价

**是。** 诗作（T1–T6 的作品）、引擎、测试样本、期望值都出自同一个模型。
这是本项目的结构性缺陷，靠流程（先写期望、后跑引擎）只能部分缓解。
**唯一彻底的解法是由外部审核者指定样本与期望。**

## 7.3 规则与数据是否互相矛盾

发现两处：

1. `POLICY_LENIENT` 白名单 11 字，与「不得按格律选音」的原则存在张力 ——
   它允许在固定位取任一读音。已在代码注释与报告中标为「工程政策」，不计 PASS。
2. 半韵处理：引擎说「无法判定」，但《词林正韵》原书是有确定答案的（按字分配）。
   这不是矛盾，是本项目缺数据。已在 03 报告中写明。

| 缺口 | 影响 |

`平水韵_全表_繁体.json`（见第四章）。这是最需要外部核验的一项。

# 第十二章　自我审计

**1. 白名单 11 字可能被认为是「换个名字的选音」。**
`POLICY_LENIENT` 允许「望、看、听、忘、凭、漫、叹、教、令、醒、过」在固定位取任一读音。
我没有为这 11 个字提供任何反切或义训依据，只在代码注释里说「诗家历来混用」。
这是本轮最容易被击穿的一点。若审核不认可，正确做法是清空白名单，
代价是名篇待确认数从 48 升到约 60。

**2.「待确认」可能被当成「合格」使用。**
退出码把 `待确认` 与 `合格` 同样返回 0。若有人拿退出码做 CI 门禁，
就会出现「满篇待确认但流水线全绿」。这是设计上的隐患，我选择保留（因为「待确认」确实不是违律），
但必须让使用者知道。更稳的做法是给它单独退出码。

**3. 韵书地基未核验，所有结论都可疑。**
我可以逐字引用《钦定词谱》，但对平水韵字表一个字也引不出来。
「收」在去声二十六宥、「留」在去声二十六宥，我怀疑是源数据误收，但**没有依据否认**。
在这个前提下，本报告里所有「某字为两读」的陈述都只是「源表如此记载」，不是「事实如此」。

**4. 测试通过率高，可能只是因为我把期望写松了。**
黄金样本的期望是 `判定 ∈ {合格, 待确认}` 且 `违律 = 0`，而不是 `判定 = 合格`。
这个松紧是我定的。如果收紧到「必须合格」，6 个黄金样本会全部失败 ——
因为两读字让它们都有待确认项。**我把标准定在了引擎能做到的位置上**，这是自利偏差的典型形态。

**5. 改过检查器口径，可能被视为「改测试迁就代码」。**
`run_tests.py` 的不变量 I5 最初写成「违律条数 == 逐字 FAIL 数」，古体样本与静夜思都报违规。
我改成了「有 FAIL 必有记录」。理由是原假设本身错了（押韵、粘对错误不落在单字上），
但审核者完全有理由怀疑这是为了让测试变绿。修改前后的代码与理由都留在 `09_代码修复记录.md` 第七节，
请自行判断。

**6. 古体识别只覆盖一半。**
仄韵体能识别，平韵古体不能。《静夜思》至今被判「不合近体格律」。
我没有加「像古体就放过」的启发式，因为那会削弱对真实出律的检出。这是一个明确的取舍，不是遗漏。

**7. 我在报告里用了不少「证明」类的措辞。**
比如「反例证明修改生效」。严格说，V03 只证明了「在这一个构造样本上行为正确」，
不构成对《钦定词谱》全谱的证明。这类措辞在本报告中应理解为「该用例支持」，而非数学意义的证明。
